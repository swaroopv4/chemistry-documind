# Hybrid retrieval

Default `RETRIEVAL_MODE=hybrid` combines independent Pinecone dense cosine candidates and SQLite FTS5 BM25 keyword candidates from the entire locally indexed corpus. It does not merely apply keywords to dense top-k results. Reciprocal rank fusion adds `1/(60+rank)` from each branch, deduplicates vector IDs and selects final top-k. This is rank fusion, not a learned reranker or a confidence probability. [SQLite BM25 documentation](https://www.sqlite.org/fts5.html#the_bm25_function), [Pinecone hybrid overview](https://docs.pinecone.io/guides/search/hybrid-search).

The existing cosine index, namespace, embeddings, Groq model and API keys are retained. BM25 uses built-in SQLite without an extra hosted service, sparse embedding request, dependency or API key. The shared `data/state.sqlite3` volume persists its chunks. Include that volume when migrating to cloud or rebuild from Pinecone there. Each branch requests `max(20,4*top_k)` candidates, capped at 100.

Tokenization normalizes Unicode (`H₂O` matches `H2O`), removes common question stopwords, preserves recognized formula/element case (`CO` differs from `Co`) and retains CAS-style IDs and atom labels. Encoded tokens prevent questions from becoming FTS query syntax. This is a limited lexical tokenizer, not a chemical nomenclature/structure parser; synonyms and alternative formulas can still require semantic matches.

Dense candidates must meet `MIN_RETRIEVAL_SCORE` (default .25). Keyword candidates must cover at least half of the significant query terms and match a requested chemical token when present. These are evidence-admission heuristics, not proof of correctness. Access filters apply before keyword candidate selection. BM25 full-corpus statistics are not probabilities and are not directly mixed with cosine values.

New ingestion redacts common identifiers, writes Pinecone and atomically replaces the document's keyword rows. Replacement/deletion removes old/trailing keyword chunks. Failed remote writes remove the old keyword entry instead of serving stale text. UI uploads are private until reviewed/published. Celery writes the same shared keyword index used by the app.

**Documents → Rebuild keyword index from existing vectors** reads stored metadata/text without re-embedding or changing Pinecone. A complete scan is staged privately and atomically installed. Failed scans or scans exceeding 100,000 vectors retain the prior index. Concurrent app ingestions/deletions committed during scanning are preserved. Unknown names are discovered privately; existing publication policies are preserved. This is an explicit admin operation, never a startup/per-question full scan.

Student access rules apply independently to both branches, unexpected private dense hits are removed before fusion, and existing output/policy gates still run. Each keyword candidate is checked against a fresh Pinecone fetch for ID, document identity and redacted-text digest. Deleted or externally changed chunks are skipped until rebuild. Student chat exposes no raw chunks/internal filenames. Corpus/policy/retrieval-mode changes invalidate caches; exact Redis repeats still skip search/model calls.

If keyword storage or remote validation is unavailable, the request falls back to admitted dense candidates. A dense-query failure fails the request. Zero keyword chunks can mean the namespace is empty or existing vectors need backfilling. Keyword verification adds remote-fetch latency on misses. Improved answer quality on the user's corpus requires a representative evaluation set; the functional fixtures alone do not establish it.

Admin cards show branch provenance, original cosine, BM25, term coverage and RRF separately. Keyword-only evidence has no dense cosine; telemetry records it as missing. Drift checks skip mixed dense/hybrid or missing-score windows. Set `RETRIEVAL_MODE=dense` and restart app/worker for semantic-only retrieval. Regression tests cover that compatibility path plus real BM25, fusion and hybrid student privacy behavior.
