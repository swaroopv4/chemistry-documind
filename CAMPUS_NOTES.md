# Admin and student application

Hybrid retrieval now combines semantic Pinecone candidates and independent local BM25 candidates using reciprocal rank fusion. Both branches enforce the same private/published document boundary. Existing vectors can be backfilled without re-embedding; new ingestions update both indexes. See HYBRID_NOTES.md for migration, ranking and monitoring limits.

The working Phase 4 source was backed up before changes, without credentials or private data. The tutorial pipeline now has verified UCI identity support, separate admin/student views, batch ingestion, document publication/privacy controls, dedicated answer Redis, runtime cache settings and audit/health screens. This is a customized application beyond the original tutorial.

## Views and access

The same deployed application serves both roles. A verified managed @uci.edu Google identity is required in production. ADMIN_EMAILS grants the admin role only to explicitly listed UCI addresses; other accepted UCI accounts get student chat. The current private configuration uses the owner-specified admin email. Roles are checked on every rerun and never come from an email form or user-selectable public role. Local loopback Compose permits an explicit owner admin preview until OAuth is configured. Its Student chat workspace previews the user experience. The production Compose disables that bypass; the launcher refuses it in production and refuses missing OAuth or an HTTP callback.

Student chat offers questions, answers, safe source labels/locations, a new-conversation action and sign-out. It contains no upload, removal, chunk inspection, evaluations, settings, Redis controls or logs. Conversations remain in that user's browser session, capped at 100 messages and cleared when identity/role changes. Each question is independently retrieved; include the relevant compound/topic in follow-ups. Raw chunks, original filenames and internal document identifiers are not rendered to students. Admin retains Ask/testing, job queue, lexical metrics, RAGAS, cost Dashboard and Documents, with an added Logs & Redis tab.

## Ingestion and document privacy

Documents supports up to 50 files per background batch, 20 MB each and 250 MB combined. Each file has a separate job ID; one submission failure does not hide the others. Duplicate filenames in the same batch are rejected. Ambiguous broker publication retains the job ID/file for tracking before retrying. Single-file testing remains, with local parsing/chunk preview before any embedding/index call. PDF, PPT, PPTX, DOCX, MOL2 and CIF are still supported.

New/replaced documents stay private while ingestion runs and until explicitly reviewed/published. Documents marked as personal are excluded entirely from student retrieval and cached answers. Mixed documents should be anonymized into a reviewed copy before publication. The admin checkbox and review acknowledgment control publication; basic privacy guards cannot be disabled for students. Use a generic student source label, rather than a filename containing someone's name.

Existing vectors are not deleted or automatically published. Discover existing vector documents scans up to 10,000 IDs in the existing embedding namespace and registers their names privately, reporting if the scan is incomplete. Smaller sampled document Refresh/removal remains available. Review/publish each document that students should use. The server sends a published-document filter to Pinecone, rejects unexpected private matches after retrieval and rechecks policy before returning an answer. Changing visibility/labels invalidates cache scopes and clears answer caches. Files are made private before removal/replacement so eventual consistency cannot restore student access through this app.

Common labeled personal identifiers and credentials are redacted before new embeddings/index writes. Legacy vectors are sanitized on retrieval; they are not silently rewritten. Student questions pass regex checks and Groq structured classification for chemistry relevance, personal-data requests and prompt injection. Candidate answers are buffered, redacted and checked by a separate output privacy gate before display/cache. Safety-provider failures refuse the response instead of displaying unchecked content. Private document exclusion and hiding raw chunks are the strongest safeguards; model/regex checks cannot establish universal immunity to jailbreaks or perfect detection of all personal information.

The backend prompt uses the precision of a chemistry researcher: evidence-only answers, citations, reported units/significant figures, source disagreements and explicit uncertainty. It does not authorize unsupported scientific properties, outside facts or personal information. Unrelated questions receive the request to ask about chemistry/shared chemistry documents. No automatic retry/escalation workflow was inferred from the owner's unfinished sentence about repeated unsuccessful answers.

## Redis and cache settings

Ingestion Redis retains its queue and result store. A separate answer Redis has a 128 MB memory ceiling and no public port in cloud Compose. App-managed cache modes are LRU (recent use), FIFO (last new questions), LFU (frequently asked), all-with-expiry, and disabled. Admin capacity choices include 50, 100, 250, 500 and 1000. TTL ranges from 60 seconds to 7 days. All-with-expiry ignores entry count, but still expires answers and has a Redis memory backstop; it does not mean permanent unlimited storage. Default is LRU/100/one hour. SQLite semantic cache uses corresponding bounds and policy; semantic matching is off for students by default because similar chemistry questions can require different answers.

Approved exact repeats hit Redis before embedding, retrieval or model calls. Cache keys preserve case (CO differs from Co), include audience/corpus revision/model/prompt/security settings, and do not mix admin/private answers with student/public answers. Hits are rechecked against current publication policy. New questions still incur input/output safety calls; they are logged with their purpose in the cost Dashboard. Cached approved answers avoid those repeated model calls. Cache/provider/storage failure behavior is documented: answer-cache outages fall back to normal retrieval; the separate per-user rate limit is held in non-evicting broker Redis and fails closed if unavailable.

Logs & Redis displays saved strategies, capacity/expiry/top-k, cache hit/miss/memory/eviction counts, broker pending jobs, responsive workers and pseudonymous access/admin events. Clearing answer caches does not flush the ingestion queue. Unexpired stored-entry counts can include older corpus scopes awaiting TTL/eviction; those entries cannot be reused. All-with-expiry is still subject to Redis's allkeys-lru hard-memory backstop, independently of the app's chosen retention strategy. Actor identifiers are pseudonymous; logs and evaluations remain admin-only. API keys, tokens, Redis passwords and broker/cache URLs are not exposed by these screens.

## Setup and deployment limits

Groq and Pinecone are still the only AI API keys. Google sign-in needs an OAuth client ID/secret and server cookie secret; the cookie secret has been generated privately, but the OAuth client has not been supplied. Real Google sign-in and UCI Workspace consent must still be verified after registration. AUTH_SETUP.md gives the exact setup. CLOUD_DEPLOYMENT.md and compose.cloud.yaml prepare the complete Docker stack for a cloud VM, with HTTPS and private password-protected Redis. No public cloud deployment has occurred without a supplied cloud account/VM/hostname. Local Linux amd64 tests do not constitute an ARM VM build or production load test.
